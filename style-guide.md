# Style Guide

## Voice and Tone

### Voice Principles
- **Direct and actionable**: Every section should enable readers to take immediate action
- **Practical over theoretical**: Focus on real-world application
- **Outcome-focused**: Always connect activities to measurable results
- **Collaborative**: Acknowledge that innovation is a team effort

### Tone Guidelines
- Use second person ("you") to directly address the reader
- Use active voice ("Create a hypothesis" not "A hypothesis should be created")
- Be concise but complete
- Avoid jargon unless defined in glossary

## Banned Words and Phrases

### Avoid These Terms
- "Best practices" → Use "proven approaches" or "recommended methods"
- "Easy" → Use "straightforward" or specify the actual complexity
- "Just" → Be specific about the effort required
- "Simply" → Provide context for complexity
- "Obviously" → Nothing is obvious to all readers
- "Just do X" → Explain the steps and reasoning

## Callout Types

Use standardized callouts for consistency:

### Warning
```markdown
> ⚠️ **Warning**: [Critical issue or risk]
```

### Tip
```markdown
> 💡 **Tip**: [Helpful suggestion or shortcut]
```

### Note
```markdown
> 📝 **Note**: [Additional context or explanation]
```

### Checklist
```markdown
> ✅ **Checklist**: [Quick reference items]
```

### Goal
```markdown
> 🎯 **Goal**: [Desired outcome or objective]
```

### Example
```markdown
> 📖 **Example**: [Worked example or case study]
```

## Figure Captions

All figures, diagrams, and images must include:
1. **Figure number**: Sequential numbering per chapter
2. **Descriptive title**: What the figure shows
3. **Context**: Why it matters in this chapter

Format: `Figure X: [Title] - [Context]`

Example: `Figure 1: Hypothesis Canvas - Template for structuring testable hypotheses`

## Code Blocks and Examples

- Use language tags for code blocks
- Include inline comments explaining key decisions
- Show expected output when relevant
- Provide context before code examples

## Headings Structure

- Use descriptive headings that signal content
- Avoid generic headings like "Introduction" or "Conclusion"
- Use question-based headings for decision points: "Should You Build This Feature?"

## Formatting Standards

### Lists
- Use numbered lists for sequential steps
- Use bullet lists for parallel items
- Use checklists for actionable items

### Emphasis
- **Bold** for key terms and important concepts
- *Italic* for emphasis within sentences
- `Code` for technical terms, commands, or variables

### Tables
- Use tables for structured comparisons
- Include headers
- Keep cells concise

## Chapter Template Structure

Each chapter must include (in order):
1. Purpose and Outcome (frontmatter)
2. Learning Outcomes (3-5 measurable outcomes)
3. Jobs-to-Be-Done
4. Inputs
5. Activities
6. Apply It Now (interactive task)
7. Artifacts
8. Worked Example
9. Checklist
10. Self-Assessment
11. Exit Criteria
12. Dependencies & Next Steps

## Versioning

- Include version numbers in chapter headers: `# Chapter Title (v1.0)`
- Document major changes in changelog
- Use semantic versioning (major.minor.patch)

## Accessibility

- Use descriptive link text (not "click here")
- Include alt text for all images
- Ensure sufficient color contrast
- Use heading hierarchy correctly

## Consistency Checklist

Before publishing, verify:
- [ ] All callouts use standard format
- [ ] All figures have captions
- [ ] All code examples have context
- [ ] All links are descriptive
- [ ] All glossary terms are defined
- [ ] All templates are linked
- [ ] All examples are complete
- [ ] All checklists are actionable
