# 01 - Idea / Problem

**Purpose**: Initialize the workspace, create a project, and establish strong initial problem context.

## Who this is for

- Teams opening a new initiative in SwiftCNS.
- Operators creating first project-level context for collaboration.

## Outcome

You have:

- a project container,
- a first conversation,
- enough context for Assumption Discovery to start meaningful analysis.

## Why this stage matters

Most cycle quality problems start here. If project scope is too narrow or kickoff context is vague, everything downstream becomes noisier: weak assumptions, weak hypotheses, and delayed decisions. Treat this stage as system setup for learning quality, not as admin setup.

## Inputs

- SwiftCNS account access.
- Problem area or venture focus.
- Any starting context artifacts (PRD, notes, planning docs).

## Steps in SwiftCNS

### 1) Enter workspace and create a project

Reference screenshot: `../screenshots/01-workspace-dashboard.png`

- Log in via `swiftcns.ai`.
- On the dashboard, choose **Create a project**.
- Name the project around a durable problem domain (not a one-off feature).

### 2) Open project dashboard and start first conversation

Reference screenshot: `../screenshots/02-project-dashboard.png`

- On the new project dashboard, choose **Create first conversation** or **New conversation**.
- Use a conversation name that reflects the problem context your team is exploring.

### 3) Kick off the conversation with high-signal context

Reference screenshot: `../screenshots/03-kickoff-conversation.png`

- Describe the problem, audience, constraints, and what success would look like.
- Add attachments when available (PRD, research notes, strategy docs).
- Prioritize specificity over length.

### 4) Answer clarifying questions from the agent

Reference screenshot: `../screenshots/04-clarifying-questions-conversation.png`

- Respond to each question with concrete details when known.
- If unknown, state uncertainty explicitly rather than guessing.
- Treat clarifying questions as part of framing quality, not as friction.

## Quality gates

- Project scope is broad enough to support repeated cycles.
- Conversation context includes problem, audience, and constraints.
- Unknowns are documented explicitly.
- Agent has enough signal to proceed to assumption surfacing.

## Common mistakes

- Naming the project around one feature instead of a durable bet.
- Giving generic kickoff context with no user or constraint detail.
- Guessing on unknowns instead of marking uncertainty explicitly.

## Outputs

- Project created and visible in dashboard analytics.
- Kickoff conversation saved.
- Clarified context in thread history.

## Definition of done

- Team can point to one conversation that clearly frames the idea/problem.
- Next step (critical assumptions) can be executed without re-framing from scratch.
